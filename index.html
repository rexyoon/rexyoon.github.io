문제 해결 사례

01

영문 문의 폼의 지역 자동입력 실패 — 잘못된 데이터가 실제로 저장되고 있던 건

문의하기에서 딜러를 선택하면 시/도·시/군/구가 자동 입력되어야 하는데 영문에서만 동작하지 않았습니다. 공통 스크립트가 <html lang="en">일 때 지역 목록을 로마자(Seoul)로 렌더링하는 반면, DB의 딜러 지역값은 한글(서울특별시)이라 텍스트 매칭이 항상 실패하는 구조였습니다.

더 큰 문제는 매칭 실패 시 처리가 없어 플레이스홀더 문자열이 그대로 전송되고 있었다는 점으로, 실제 DB에서 지역이 시/도 선택으로 저장된 문의 8건을 확인했습니다.

  • 한글·영문 지역 사전이 인덱스 단위로 완전히 평행함을 검증한 뒤, 위치 기반 변환 방식으로 재구현
  • 매칭 실패 시 이전 값이 남지 않도록 초기화 처리 추가
  • hidden 필드를 도입해 화면은 영문 표기, 저장은 한글 단일 기준으로 통일
02

딜러 선택이 0.6초 뒤 자동 해제되던 문제

선택 직후 상태를 시계열로 계측해 원인을 특정했습니다. 자동 입력된 지역 변경을 감시 루프가 사용자 조작으로 오인해 딜러 목록을 재생성하면서 선택이 유실되는 구조였습니다.

  • 동기화 종료 시점에 기준값을 갱신
  • 목록 재생성 시에도 기존 선택을 복원하도록 이중으로 방어
03

공통 스크립트를 수정할 수 없는 제약 하의 우회 구현

영문 퀵메뉴가 전혀 동작하지 않았습니다. 원인은 공통 JS가 버튼을 한글 텍스트(빠른 메뉴)로 탐색해 영문 버튼을 찾지 못하는 것이었으나, 해당 파일은 퍼블리셔 관리 영역이라 수정할 수 없었습니다.

  • 공통 JS가 HTML을 innerHTML로 주입해 <script>가 실행되지 않는 점까지 고려
  • 기존 파일이 이미 사용 중인 인라인 이벤트 속성 방식으로 동작을 복원

작업 방식

“ 추측으로 수정하지 않고, 원인을 실측으로 확인한 뒤 고친다. ”
  • 브라우저 DOM을 직접 계측해 재현 → 수정 → 재검증
  • 내부 링크 29개 HTTP 응답 전수 확인, 외부 링크 14개 접속 확인
  • 화면 이슈도 DB를 조회해 실제 데이터 오염 여부까지 확인 후 조치
